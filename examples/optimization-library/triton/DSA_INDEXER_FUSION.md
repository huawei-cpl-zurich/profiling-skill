# DSA Lightning indexer score fusion

This source application compares an educational three-kernel GPU decomposition with the source's fused QK → ReLU → query/head weight → head sum. It claims no new optimization technique. The upstream source is pinned at `7acb9c40a6ca827e885d902b7eaee5d45457b230`; its original kernel, actual NPU test, full MIT license and third-party notice are retained beside the example. Public-export context and source hashes accompany the evidence. This standalone component does not validate the entire upstream package or downstream DSA attention/top-k selection.

The before API computes FP32 per-head QK scores into a private `[B,M,H,N]` tensor, applies the source ReLU and FP32 query/head weights into a second FP32 tensor, then performs the same head-axis sum. All three kernels run on every prepared call. The after API uses the exact source kernel body with its outer autotuner removed and its function renamed; an AST/source-hash gate checks this before compilation. Both use one program per batch/query, serial N blocks, `BLOCK_SIZE_N=128`, four warps, one stage and `multibuffer=False`. This is a prospective common configuration, not vendor-best or autotuned throughput.

Q is contiguous FP16 `[B,M,H,D]`, K contiguous FP16 `[B,N,D]`, and weights contiguous FP32 `[B,M,H]`. The result is one private contiguous FP32 `[B,M,N]` score tensor. The source's FP8 docstring is stale: its actual NPU test uses FP16/BF16 inputs and FP32 weights. This experiment fixes FP16. The implicit contiguous weight-pointer contract is checked explicitly; zero-stride broadcast views are rejected. One guard uses broadcast-valued weights materialized contiguously, including a zero-weight query and negative weights. The other guard exercises batch indexing and an N tail of one.

Q/K values are integers in `[-4,4]` divided by 64; weights are integers in that range divided by 16. With `D<=128` and `H<=64`, dot-product integer partials have magnitude at most 2048 and weighted head-sum partials at most 524288, below `2^24`. The common output denominator is 65536. All nonzero FP32 values and intermediates are exact under the verified FP16-input/FP32-accumulator/FP32-intermediate types. Independent CPU FP64 matmul, ReLU and weighted head reduction generate each expected payload once. Primary validation requires exact nonzero FP32 bits and numerical zeros; signed-zero and paired all-bit equality are secondary diagnostics. They also matched on all six observed cases.

All twelve input-only compile cells, twenty-four stage-artifact snapshots, actual executable sections/relocations, typed IR and available resource metadata passed before the first scientific CPU payload. The twelve numerical API calls then passed once each, with zero mismatches/nonfinite outputs, zero FP64 error, immutable inputs, intact canaries and private outputs. Only after all twelve passed did the four main pairs run ten complete prepared API calls per arm: eighty calls in eight captures, with no guard profiles, warmups, autotuning or additional timings. The authoritative [v2 freeze](../../../experiments/optimization-wave011/W011-02-v2.json) clarified zero-sign handling before any scientific data; v1 remains unexecuted history.

These are profiler-active measurements. Full operation spans include submission gaps between the three baseline kernels. In the smallest case, those gaps dominate the span difference; the table therefore also shows summed device-task duration. It does not establish ordinary uninstrumented latency or a physical memory-bandwidth/roofline improvement. The vendor trace contains thirty tasks per before capture (`AI_CORE` and `AI_VECTOR_CORE`) and ten per after capture (`MIX_AIC`). All attributed work is charged, including the fused task's vector component. Raw per-stage PMUs remain separate rather than averaging unrelated Cube/vector ratios.

Preparation validates CPU inputs, allocates private device copies/output/scratch, and compile-checks the bound specialization. Allocations, source-wrapper output zeroing, reference generation and initial transfers are outside both prepared APIs; both implementations overwrite every valid output. Outputs and before scratch are reused. Both arms' buffers remained resident during capture: logical allocation is reported per item and for the full pool, without claiming a measured allocator/occupancy benefit. Compiler-managed scratch/spills and physical peak memory are not established. No input/output inspection or reset occurs in the ten-call capture loop.

Prepared objects have idempotent `close()`; the generic pair runner closes them after success or failure. Collector-owned items remain live through the frozen all-case correctness gate and subsequent captures, then close together. Allocation, compile and launch use explicit logical device 0 under a guard that restores the caller's selected device. Input-only prototypes reject `run()` before launching. Compilation publishes its identity list atomically after every required stage succeeds. Numeric/layout admission occurs before backend access; the published qualification covers the frozen six cases.

The public CLI is exploratory. From any working directory, invoke `dsa_indexer.py` with an absolute script path and `--case`, `--output`, `--cache`, `--provenance`, optionally `--correctness-only`. A case is one JSON case object, with either flat dimensions or a `parameters` mapping; valid trailing newlines are accepted. The frozen collector is retained by hash in the evidence archive. Five functional tests exercise independent CPU caching, admission, partial compile failure/retry, prototype rejection, both arm orders/default dtypes, diagnostics, cleanup, caller-device restoration, signed-zero secondary behavior, real `collect_pair` identity validation and external-cwd CLI behavior. They passed locally and on GZ A3.
