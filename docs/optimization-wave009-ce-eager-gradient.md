# Cross-entropy gradient eagerness

The exact pinned joint forward/gradient kernel reduced the measured complete-operation span when a caller consumed the gradient. Loss-only calls were approximately neutral in one case and slower in the other. All twelve independent FP64 gates passed before eighty profiled API calls. This is an application of a known fusion technique; it claims no new mechanism.

These are profiler-instrumented operation spans across ten complete calls per arm, including every charged helper and Torch loss reduction. Individual samples, standard deviations, task time/union/gaps, raw supported PMUs, source/compiler identities, and all artifact hashes are in [the dataset](data/optimization-w009-ce-eager-gradient.json). All samples remain, including variable first samples. These spans do not establish ordinary application latency, allocator latency, physical traffic, occupancy, or instruction counts.

`ce_eager.Adapter` prepares immutable contiguous FP32 logits and I64 targets and returns `(loss, dx)` when `needs_grad=True`, otherwise `(loss, None)`. The scalar upstream scales only `dx`. Both arms use the same online FP32 max/sum statistics, smoothing, ignore index −100, and mean normalization. All-ignored rows produce source-convention loss zero, which differs from PyTorch's all-ignored mean NaN. The independent CPU provider uses FP64 stable log-sum-exp and the analytic derivative; fixed tolerances are loss atol/rtol 2e−5/2e−5 and gradient 3e−6/2e−5. Paired FP32 bit equality was observed for all six cases and remains secondary evidence.

BEFORE is an educational source-derived delayed-gradient implementation: save row statistics and run a separate gradient kernel only when required. Loss-only BEFORE reads the original input directly and saves no statistics. AFTER uses the exact pinned joint kernel, always copies into private workspace and computes its in-place gradient, including when the caller discards it. Both arms already avoid log-probability materialization; this study changes gradient staging and does not recount initial E10's materialization optimization.

Every API includes a common Triton copy/loss-zero helper when workspace is used, or a loss-zero-only helper for loss-only BEFORE, plus `torch.sum(dim=0, out=scalar)`. Needed nonunit upstream scaling uses the source elementwise kernel with 32 warps. The profiler accounted for all 280 tasks, including 80 `aclnnReduceSum_ReduceSumOpAiCore_ReduceSum` tasks. No unknown task kind was filtered. Private outputs and workspace are allocated once and reused. This measures prepared device computation, not the upstream Torch copy/zero implementation, fresh allocation, generic autograd, or repeated backward behavior.

The common configuration is source-controlled `BLOCK=min(2048,nextpow2(V))`, stage 1, multibuffer disabled, and FP fusion disabled. It does not use the public source's non-power-of-two 3840 maximum heuristic or claim vendor autotuner throughput. The source pin is `7acb9c40a6ca827e885d902b7eaee5d45457b230`; exact joint/multiply bodies and attributed split derivatives retain the LinkedIn/Huawei notices in `ce_eager_NOTICE`.

The capable native A3 run queried Ascend910/9382 with 24 Cube and 48 vector cores. Twelve input-only arm/case cells, covering 31 logical Triton components and 26 unique hashes, compiled before generating six cached CPU oracle payloads once. All twelve numerical calls passed before eight ten-call captures; the two guard cases had no captures. The guard cases cover ignored labels, a V=17 tail, negative upstream, and all-ignored loss-only behavior. Halos, private output ownership, output None/arity, and immutable original inputs passed. Full ELF/text/relocation hashes and compiler resources were retained before arithmetic. There were no scientific retries, warmups, autotuning, extra unprofiled timing, or post-data configuration changes. Startup, run/validation, and capture/export use bounded 600-second watchdogs, with device and both host export locks; cleanup confirmed no live owned process-group members, free locks, and fresh healthy idle hardware.

Five functional NONFROZEN CPU/mock tests passed locally and on the selected A3 runtime. They exercise the independent oracle against FP64 PyTorch on unrelated inputs, domain/layout/dtype/None admission, negative upstream/all-ignored behavior, component counts, transactional compilation after a late failure, non-executable probes, repeated adapter order and default dtype, canaries/input immutability, and external-working-directory CLI success/error behavior with strict JSON parsing.
